# 프로젝트 개요

**HUFS.Dev**는 한국외국어대학교 학생들이 개발 관련 정보와 경험을 공유하고, 함께 성장할 수 있도록 설계한 `대학 개발자 커뮤니티 플랫폼`입니다.

기존에는 개발 스터디, 프로젝트 모집, 기술 질문, 회고와 같은 활동이 여러 채널에 흩어져 있어 정보가 축적되지 않거나 
필요한 사람에게 적절히 연결되지 않는 문제가 있었습니다.

또한 학교 커뮤니티 안에서도 개발자들에게 특화된 소통 공간과 활동 동기를 만들어주는 구조는 부족했습니다.

HUFS.Dev는 다양한 개발 관련 게시판, 랭킹·뱃지, 활동 기반 커뮤니티 시스템을 통해 단순한 정보 게시 공간을 넘어, `기여가 기록되고 활동이 축적되는 개발자 커뮤니티`를 만드는 것을 목표로 했습니다.

&nbsp;

# 시스템 아키텍처 설계

![시스템 아키텍처](https://eaalkymxyfskjojh.public.blob.vercel-storage.com/portfolio/hufsdev/hufsdev-architecture.png)

HUFS.Dev의 인프라는 **AWS 서비스를 직접 설계·구성해보며 학습하는 것**을 주요 목표로 두고 설계했습니다.

단순히 애플리케이션을 서버에 배포하는 데 그치지 않고, 웹 서비스의 요청이 애플리케이션까지 전달되는 과정과 데이터베이스, 캐시, 파일 스토리지, CDN, 배포 파이프라인을 각각 분리해 구성했습니다.
이를 통해 실제 서비스에서 각 인프라 요소가 어떤 책임을 담당하는지 직접 경험하는 데 초점을 맞췄습니다.

&nbsp;

## 프론트엔드 배포

프론트엔드는 Vercel에 배포해 정적 자산을 빠르게 제공하도록 구성했습니다. 
프론트 배포를 백엔드 릴리즈와 분리하여 UI 변경을 더 빠르게 반영하고, 
백엔드 배포 리스크에 영향을 받지 않도록 했습니다.

&nbsp;

## 백엔드 인프라

백엔드 트래픽 흐름은 **Route 53 → ALB → Nginx → Spring Boot** 구조로 구성했습니다. 
Route 53에서 도메인을 관리하고, ALB가 외부 HTTPS 요청을 받아 EC2의 Nginx로 전달하도록 구성했습니다.
EC2 내부의 Nginx는 리버스 프록시 역할과 함께 현재 활성화된 Spring Boot 컨테이너로 요청을 전달합니다.

데이터 계층은 **PostgreSQL(RDS)** 과 **Redis(ElastiCache)** 로 분리했고, 
파일 업로드는 **S3**, 정적 파일 조회는 **CloudFront** 를 통해 제공하도록 구성했습니다. 

또한 애플리케이션 이미지는 **GitHub Actions → ECR → EC2 docker pull** 흐름으로 배포되도록 구성했습니다.

&nbsp;

### 배포 전략

애플리케이션 배포에는 **Nginx upstream 전환을 이용한 Blue-Green 방식**을 적용했습니다.
하나의 EC2 내부에 서로 다른 포트를 사용하는 Blue와 Green Spring Boot 컨테이너를 두고, 새 버전을 비활성 환경에 먼저 실행한 뒤 정상 동작을 확인하면 Nginx의 upstream을 새 컨테이너로 전환하도록 구성했습니다.

새 버전과 기존 버전을 일정 시간 함께 유지할 수 있기 때문에 배포 중 애플리케이션을 종료했다가 다시 실행하는 방식보다 서비스 중단 시간을 줄일 수 있고, 문제가 발생했을 경우 Nginx의 라우팅 대상을 기존 컨테이너로 되돌리는 방식으로 빠르게 복구할 수 있습니다.

다만 Blue와 Green 환경이 각각 독립된 서버로 구성된 형태는 아니며, 동일 EC2 내부에서 애플리케이션 컨테이너를 이중화하고 Nginx로 전환하는 구조입니다. 따라서 EC2 자체의 장애까지 격리할 수 있는 구성은 아닙니다.

### + 왜 Blue-Green 배포를 선택했는가...

배포 전략을 설계할 때는 새 버전 배포 과정에서 서비스 중단을 줄이고, 문제가 생겼을 때 이전 버전으로 빠르게 복구할 수 있는 구조를 우선적으로 고려했습니다.

당시에는 Blue-Green 배포를 중심으로 먼저 학습하고 적용했는데, 동일한 애플리케이션을 두 개의 버전으로 분리해 두고 라우팅만 전환하면 된다는 점에서 구조가 직관적이고 운영 흐름을 이해하기 쉽다고 판단했습니다.

Rolling이나 Canary와 같은 방식도 검토할 수 있지만, HUFS.Dev 규모에서는 여러 인스턴스에 걸쳐 버전을 점진적으로 교체하거나 트래픽 비율을 나누어 검증하는 구조보다 Blue와 Green 두 실행 환경을 두고 전환하는 방식이 구현과 동작 원리를 이해하기에 적합했습니다.

&nbsp;

### 파일 스토리지 및 CDN

사용자가 업로드한 파일은 애플리케이션 서버의 로컬 디스크가 아닌 S3에 저장하도록 구성했습니다.
파일 저장 위치를 애플리케이션 서버와 분리함으로써 서버가 교체되거나 컨테이너가 재생성되더라도 업로드 파일이 영향을 받지 않도록 했습니다.

파일 조회는 CloudFront를 통해 S3 객체를 제공하도록 구성했습니다. CloudFront의 Edge Location을 통해 콘텐츠를 전달하고 캐싱할 수 있으므로, 모든 파일 요청을 애플리케이션 서버가 직접 처리하지 않아도 됩니다.

이를 통해 애플리케이션 서버는 비즈니스 로직 처리에 집중하고, 파일 저장과 전송은 별도의 인프라가 담당하도록 책임을 분리했습니다.

&nbsp;

## + 설계 과정에서 얻은 인사이트

이 아키텍처는 처음부터 최소 비용을 목표로 설계한 구조라기보다, **AWS의 여러 서비스를 직접 구성하고 각 서비스가 어떤 문제를 해결하는지 경험하는 것**에 중점을 둔 구조였습니다.

하지만 실제로 운영하면서 월 인프라 비용이 약 60달러까지 발생했고, 이를 통해 기술적으로 구성 가능한 아키텍처와 프로젝트 규모에 적합한 아키텍처는 다를 수 있다는 점을 체감했습니다.

AWS의 로드밸런서와 HTTPS 요청 전달 구조를 직접 구성해보기 위해 ALB를 사용했지만, HUFS.Dev은 단일 EC2에서 애플리케이션을 운영하고 있었기 때문에, 현재 규모만 놓고 보면 Nginx에서 직접 HTTPS 종단과 리버스 프록시를 담당하도록 구성해 ALB를 제거하는 선택지도 있었습니다.
또한 동일 EC2 내부에서 Blue와 Green 컨테이너를 운영하고 있었기 때문에, ALB가 여러 애플리케이션 서버 사이의 트래픽을 분산하는 역할을 충분히 활용하고 있던 구조도 아니었습니다.

결국, 인프라 설계에서는 기능 구현뿐 아니라 `트래픽 규모`, `운영 복잡도`, `비용 대비 효용`까지 함께 고려해야 한다는 점을 배웠습니다.
