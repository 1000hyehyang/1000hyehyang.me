# EXPLAIN ANALYZE 기반 조회 성능 최적화

어디더라는 공동 방에 저장된 장소를 지역·카테고리·영업시간 조건으로 필터링하고 평가해 데이트 코스를 생성합니다. 코스 생성 과정에서 조건에 맞는 후보를 모두 조회하므로 데이터 규모가 커질수록 조회 비용이 증가할 수 있어, 후보 1만 건 환경에서 API 응답 성능을 측정했습니다.

### 문제 및 원인

✓ 로컬 합성 후보 10,000건 조회에서 DB 실행시간은 59.374ms였지만 API p95는 1,215.85ms였습니다.
DB 실행시간만으로 설명되지 않는 차이를 바탕으로 넓은 조회 결과를 애플리케이션으로 전달하고 Hibernate 엔티티로 materialization하는 과정의 비용을 의심했습니다.

✓ `EXPLAIN (ANALYZE, BUFFERS)`에서 플래너가 약 5KB로 추정한 row width와 `DISTINCT` 정렬 과정의 5,848kB 디스크 `external merge`를 확인했습니다.

### 해결 과정

✓ 후보 평가에 사용하지 않는 연관 엔티티의 fetch join을 제거하고, 평가에 필요한 연관 값은 **scalar projection**으로 조회했습니다.

✓ 기존 후보 쿼리는 영업시간의 유효 여부만 확인하고 실제 영업시간은 따로 조회했습니다. 이를 후보 조회에서 함께 가져오도록 바꿨습니다.

### 결과

✓ 변경 후 플래너의 예상 row width는 **약 5KB → 509B**로 감소했고, 정렬 방식은 디스크 `external merge`에서 메모리 `quicksort`로 바뀌었습니다.

✓ 동일 조건에서 **DB 실행시간 59.374ms → 32.082ms, API p95 1,215.85ms → 187.18ms**로 감소했습니다.

# Spring Cache 프록시 우회 문제 해결

장소 저장 시 주소를 지역으로 변환하고 Kakao 카테고리를 서비스의 카테고리·태그로 매핑합니다. 지역·분류 정보는 변경 빈도가 낮은 반면 저장 요청마다 반복 조회되는 기준정보였습니다.
### 문제 및 원인

✓ `@Cacheable` 적용 후에도 지역·분류 기준정보를 각각 5회 조회했을 때 SQL이 총 10회 실행됐습니다.

✓ Hibernate Statistics로 확인한 결과, **같은 Bean 내부 호출이 Spring Cache 프록시를 우회하는 self-invocation**이 원인이었습니다.

### 해결 과정

✓ 캐시 로딩 책임을 별도 Provider Bean으로 분리하고, **Caffeine 캐시**에 TTL과 최대 항목 수를 설정했습니다.

✓ 동일 키에 대한 동시 요청이 중복 DB 조회로 이어지지 않도록 `@Cacheable(sync = true)`를 적용했습니다.

### 결과

✓ 호출 구조를 수정한 뒤 최초 조회에서는 지역·분류 로딩을 위한 SQL 2회만 실행됐고, 이후 동일 정보를 5회 재조회했을 때는 **SQL이 0회 실행**됐습니다.

✓ 8개 스레드가 **동시에 최초 조회를 수행한 경우**에도 SQL은 지역·분류 각각 1회씩, **총 2회**만 실행되는 것을 검증했습니다.

# Google OAuth2 기반 웹·Android 인증 설계

어디더라는 웹과 Android 앱을 함께 지원하며, 두 클라이언트가 동일한 백엔드 API를 사용합니다. 이에 Google 로그인 이후 토큰 전달 방식은 클라이언트 특성에 맞게 나누고, API 인증은 공통 Bearer JWT로 통일했습니다.

### ① 요구사항

✓ 웹과 Android가 각각 Google 로그인 결과를 받아 동일한 API에 인증된 요청을 보낼 수 있어야 했습니다.

✓ Access Token 만료 후에도 로그인 상태를 유지할 수 있어야 하며, 토큰 갱신과 로그아웃 시 Refresh Token의 수명주기를 관리할 수 있어야 했습니다.

✓ 웹에서 쿠키로 Refresh Token을 전송하는 요청에는 CSRF 검증이 필요했습니다.

### ② 설계

✓ **로그인 완료 방식은 클라이언트별로 나누고**, API 인증은 JWT로 통일했습니다.
웹은 OAuth2 로그인 후 HttpOnly Refresh Token 쿠키를 받고, 리다이렉트로 전달된 일회용 티켓을 Access JWT로 교환합니다. Android는 PKCE S256을 적용한 일회용 인증 코드 교환을 거쳐 두 토큰을 응답 본문으로 받습니다. 이후 두 클라이언트 모두 `Authorization: Bearer` 헤더로 API를 호출합니다.

✓ **Access Token은 JWT로 검증하고 Refresh Token은 서버에서 관리했습니다.**
Access Token은 유효기간 10분인 JWT로 발급해 일반 API 요청에서 서명과 만료를 검증합니다. Refresh Token은 원문 대신 해시를 DB에 저장하고, 갱신 시 기존 토큰을 폐기한 뒤 새 토큰을 발급합니다. 로그아웃 시에도 해당 Refresh Token을 폐기합니다.

✓ **웹의 쿠키 기반 갱신·로그아웃 요청에는 CSRF 토큰 검증을 적용했습니다.**
`XSRF-TOKEN` 쿠키와 `X-XSRF-TOKEN` 헤더를 대조해 브라우저가 Refresh Token 쿠키를 자동 전송하는 요청을 검증합니다.

### ③ Trade-off

✓ Refresh Token을 DB에서 관리하므로 갱신과 로그아웃에는 상태 조회와 변경이 필요합니다. 대신 일반 API의 JWT 인증은 인증용 DB·Redis 세션 조회 없이 처리합니다.

✓ Access Token blacklist는 두지 않았습니다. 로그아웃 후 기존 Access Token이 최대 10분간 유효할 수 있는 대신, 일반 API 인증 경로에서 별도의 토큰 상태 저장소를 조회하지 않도록 했습니다.

# 프로젝트 개요

**어디더라**는 인스타그램 릴스, 유튜브, 네이버 블로그 등 SNS 콘텐츠를 통해 발견한 장소를 저장하고, 이를 기반으로 `사용자 조건 기반 데이트 코스 자동 생성`을 지원하는 서비스입니다.

기존에는 SNS에서 마음에 드는 장소를 발견해도 별도로 기록하거나 다시 찾기 어려웠고, 저장하더라도 지도, 메모, SNS 등 여러 도구에 분산되어 관리되면서 
사용자가 원하는 흐름에 맞춰 코스를 구성하는 데 추가적인 시간과 노력이 필요했습니다.

어디더라는 SNS 공유 기능을 통해 장소를 서비스 내부에 구조화된 데이터로 저장하고, 사용자가 선택한 지역과 카테고리, 그리고 원하는 순서를 기반으로 
조건에 맞는 장소들을 조합하여 코스를 자동으로 생성합니다.

이를 통해 단순 저장을 넘어 `발견 → 저장 → 코스 생성`까지 이어지는 흐름을 지원하도록 설계했습니다.
