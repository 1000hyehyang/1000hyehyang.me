# EXPLAIN ANALYZE 기반 조회 성능 최적화

### 문제 및 원인
로컬 합성 후보 10,000건 조회에서 DB 실행시간은 59.374ms였지만 API p95는 1,215.85ms였습니다. DB 실행시간만으로 설명되지 않는 차이를 바탕으로 넓은 조회 결과를 애플리케이션으로 전달하고 Hibernate 엔티티로 materialization하는 과정의 비용을 의심했습니다. `EXPLAIN (ANALYZE, BUFFERS)`에서 플래너가 약 5KB로 추정한 row width와 `DISTINCT` 정렬 과정의 5,848kB 디스크 `external merge`를 확인했습니다.

### 해결 과정
`RoomPlace`를 제외한 불필요한 연관 엔티티 materialization을 제거하고, 필요한 필드만 조회하는 **scalar projection**으로 변경했습니다. 별도로 조회하던 영업시간 데이터도 하나의 쿼리로 통합했습니다.

### 결과
예상 row width가 **약 5KB → 509B**로 줄어 디스크 정렬 대신 메모리 `quicksort`가 사용됐습니다. 동일 조건에서 **DB 실행시간 59.374ms → 32.082ms, API p95 1,215.85ms → 187.18ms**로 감소했습니다.

# Spring Cache 프록시 우회 문제 개선

### 문제 및 원인
`@Cacheable` 적용 후에도 동일 기준정보를 5회 조회할 때 SQL이 10회 실행됐습니다. Hibernate Statistics로 확인한 결과, 같은 Bean 내부 호출이 Spring Cache 프록시를 우회하는 self-invocation이 원인이었습니다.

### 해결 과정
캐시 로딩 책임을 별도 Provider Bean으로 분리하고, Caffeine에 TTL·maximum size·`sync=true`를 적용했습니다.

### 결과
개선 전 동일 조회 5회에서 발생하던 **SQL 10회를 최초 cold load 시 2회로 줄였고, 이후 warm 조회 5회에서는 SQL이 0회 실행**됐습니다. 또한 **8개 스레드의 동시 cold miss에서도 SQL이 2회만 실행**되는 것을 검증했습니다.

# 외부 API 호출 병렬화 및 호출 수 최적화

### 문제 및 원인
장소 후보별 외부 API 호출을 순차 처리하면서 후보 수에 비례해 I/O 대기시간이 누적됐습니다.

### 해결 과정
서로 독립적인 장소 검색을 **동시성 상한이 있는 병렬 처리**로 전환해 I/O 대기시간을 겹쳐 실행했습니다. 검색 전략도 조정해 실패 시 반복되는 불필요한 API 호출을 제거했습니다.

### 결과
후보 12개·호출당 50ms의 로컬 합성 지연 조건에서 **batch p95 736.83ms → 62.00ms**로 감소했습니다. 동시에 후보당 최악의 외부 API 호출 횟수를 **9회 → 5회**로 줄였습니다.

# 프로젝트 개요

**어디더라**는 인스타그램 릴스, 유튜브, 네이버 블로그 등 SNS 콘텐츠를 통해 발견한 장소를 저장하고, 이를 기반으로 `사용자 조건 기반 데이트 코스 자동 생성`을 지원하는 서비스입니다.

기존에는 SNS에서 마음에 드는 장소를 발견해도 별도로 기록하거나 다시 찾기 어려웠고, 저장하더라도 지도, 메모, SNS 등 여러 도구에 분산되어 관리되면서 
사용자가 원하는 흐름에 맞춰 코스를 구성하는 데 추가적인 시간과 노력이 필요했습니다.

어디더라는 SNS 공유 기능을 통해 장소를 서비스 내부에 구조화된 데이터로 저장하고, 사용자가 선택한 지역과 카테고리, 그리고 원하는 순서를 기반으로 
조건에 맞는 장소들을 조합하여 코스를 자동으로 생성합니다.

이를 통해 단순 저장을 넘어 `발견 → 저장 → 코스 생성`까지 이어지는 흐름을 지원하도록 설계했습니다.
