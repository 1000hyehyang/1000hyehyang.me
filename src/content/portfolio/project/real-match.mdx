# 프로젝트 개요
![Overview](https://eaalkymxyfskjojh.public.blob.vercel-storage.com/portfolio/real-match/overview.png)
![핵심 기능](https://eaalkymxyfskjojh.public.blob.vercel-storage.com/portfolio/real-match/core.png)

**RealMatch**는 브랜드와 마이크로 인플루언서가 협업 상대를 찾고 제안, 협의, 피드백, 완료까지의 과정을 `하나의 흐름 안에서 관리할 수 있도록 설계한 협업 관리 플랫폼`입니다.

기존 인플루언서 협업은 메신저, 이메일, 문서가 분산되어 진행되며 협업 상태를 명확히 추적하기 어렵고 일정 누락이나 요구사항 전달 오류가 반복적으로 발생했습니다.

**RealMatch**는 협업 과정을 서비스 내부의 상태로 관리하여 단순 매칭 서비스가 아니라 실제 협업 운영을 지원하는 시스템으로 동작하도록 만드는 것을 목표로 했습니다.

# FCM 푸시 & 이메일 알림 시스템 설계

![알림 시스템](https://eaalkymxyfskjojh.public.blob.vercel-storage.com/portfolio/real-match/notification.png)

**RealMatch**는 협업 매칭 플랫폼 특성상 사용자가 항상 서비스에 접속해 있지 않습니다. 
제안 수신, 지원 요청, 매칭 완료는 빠른 확인이 필요한 이벤트이지만 WebSocket과 SSE는 연결이 유지된 사용자에게만 전달할 수 있습니다.

오프라인 사용자에게도 알림을 전달하기 위해 FCM 기반 Web Push를 사용하고, 이메일을 보조 채널로 함께 구성했습니다.

### ① 요구사항

✓ 서비스에 접속하지 않은 사용자에게도 제안 수신, 지원 요청, 매칭 완료와 같은 주요 협업 이벤트를 전달해야 했습니다.

✓ 확정된 비즈니스 이벤트만 알림으로 전달하고, FCM·이메일의 지연이나 장애가 핵심 요청에 영향을 주지 않아야 했습니다.

✓ 알림 유형별 지원 채널과 사용자의 수신 설정에 따라 푸시 알림과 이메일을 발송해야 했습니다.

### ② 설계

✓ **DB와 MQ 사이의 유실 구간을 줄이기 위해** `Transactional Outbox`**를 적용했습니다.** 
비즈니스 데이터와 발송 작업을 같은 트랜잭션에 저장해, DB 커밋 이후 MQ 발행 전에 서버가 중단되더라도 처리할 작업이 남도록 했습니다.

✓ **외부 발송은 RabbitMQ를 통해 핵심 요청과 분리했습니다.**
FCM·이메일 호출을 비동기로 처리하고 발송 결과를 DB에 기록해, 외부 서비스의 지연과 장애가 제안·매칭 처리로 전파되지 않도록 했습니다. 
실패하거나 처리 중 중단된 작업은 저장된 상태를 기준으로 재처리했습니다.

✓ **중복 생성과 재처리는 DB를 기준으로 제어했습니다.** 
이벤트 ID + 알림 유형 + 수신자 ID를 멱등성 기준으로 두고 `Unique Constraint`를 적용해 동일 이벤트의 중복 생성을 제한했습니다. 


### ③ Trade-off

✓ Outbox를 적용하면서 추가 테이블, Polling, Recovery Scheduler 등 운영 복잡도가 증가했습니다. 
그럼에도 알림 유실을 줄이고 실패한 작업을 추적·재처리할 수 있는 구조를 우선했습니다.

# 실시간 WebSocket 채팅 시스템 설계

![채팅 시스템](https://eaalkymxyfskjojh.public.blob.vercel-storage.com/portfolio/real-match/chat.png)

**RealMatch**의 채팅은 단순 대화 기능이 아니라 브랜드와 크리에이터의 협업 진행을 위한 주요 인터페이스입니다. 
사용자는 채팅을 통해 일정·요구사항·피드백을 조율하며, 지원·제안·매칭 결과와 같은 협업 상태도 시스템 메시지로 전달받습니다.

STOMP의 구독 모델을 이용해 채팅방 단위로 메시지를 브로드캐스트하고, STOMP CONNECT 단계에서 JWT 인증을 수행한 뒤 SUBSCRIBE 단계에서 채팅방 참여 권한을 검증했습니다.
메시지는 DB에 영속화하여 연결이 끊기더라도 REST 조회를 통해 대화 내역을 복구할 수 있도록 구성했습니다.

### ① 요구사항

✓ 채팅방 참여자는 실시간으로 메시지를 주고받고, 이전 대화 내역을 다시 조회할 수 있어야 했습니다.

✓ 제안 수락, 지원 결과, 매칭 정보와 같은 협업 상태가 채팅방의 시스템 메시지로 함께 기록되어야 했습니다.

✓ 인증된 사용자만 STOMP 연결을 완료하고, 해당 채팅방의 참여자만 메시지를 구독할 수 있어야 했습니다.

### ② 설계

✓ **협업 상태와 시스템 메시지를 같은 트랜잭션에 저장했습니다.** 
두 데이터가 따로 저장되면 실제 협업 상태와 사용자가 보는 채팅 기록이 달라질 수 있습니다. 
비즈니스 이벤트를 커밋 전에 처리해 협업 상태, 채팅방, 시스템 메시지가 함께 커밋되거나 함께 롤백되도록 했습니다.

✓ **WebSocket 전송은 트랜잭션 커밋 이후에 실행했습니다.** 
WebSocket은 DB 트랜잭션에 참여하지 않으므로 먼저 전송하면 이후 롤백된 내용을 회수할 수 없습니다. 
메시지를 DB에 먼저 확정한 뒤 실시간으로 전달하고, 연결이 끊기거나 전송에 실패해도 저장된 내역을 REST API로 다시 조회할 수 있게 했습니다.

✓ **중복 저장과 최신 상태의 역행을 DB에서 제어했습니다.** 
동시 요청에서는 저장 전 조회만으로 중복을 완전히 차단하기 어렵기 때문에 시스템 메시지와 사용자 메시지에 각각 `Unique Constraint`를 적용했습니다. 
마지막 메시지와 읽음 위치 역시 더 최신인 경우에만 갱신하도록 조건부 UPDATE를 사용했습니다.

### ③ Trade-off

✓ 제안 수락·지원 결과와 함께 생성되는 시스템 메시지의 저장에 실패하면 상태 변경 요청도 실패하므로 사용자가 다시 시도해야 합니다. 
핵심 기능이 채팅 저장에 의존하는 결합을 감수하는 대신, 협업 상태만 변경되고 확인 가능한 안내 기록이 남지 않는 상황을 막는 것을 우선했습니다.

✓ 커밋 이후 WebSocket 전송의 자동 재시도는 보장하지 않습니다. 
현재는 저장된 메시지를 다시 조회할 수 있다는 점을 활용해 별도 Outbox를 두지 않았습니다.
